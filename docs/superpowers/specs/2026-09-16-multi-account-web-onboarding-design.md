# Telegram MCP: веб-подключение нескольких аккаунтов

Статус: согласовано направление; документ ожидает финального просмотра перед реализацией.

Этот документ заменяет однопользовательские части исходной спецификации `2026-09-16-telegram-mcp-design.md`. Требования исходной спецификации к HTTPS, Bearer-токену, безопасным ошибкам, отсутствию содержимого сообщений в логах и явному выбору отправителя сохраняются.

## Результат

`tg-mcp serve` всегда запускает HTTP-сервер, даже если ни один Telegram-аккаунт ещё не авторизован. Владелец открывает корневую страницу, подключает несколько пользовательских аккаунтов через независимые QR/2FA-потоки и при необходимости добавляет несколько ботов. MCP-клиенты явно передают стабильный `account_id` или `bot_id` при каждой операции.

Один общий MCP-токен первой версии разрешает доступ ко всем подключённым аккаунтам и ботам. Разграничение прав между агентами не входит в эту версию.

## HTTP-поверхность

- `GET /` возвращает локальную HTML/JS-страницу настройки без секретов и внешних ресурсов.
- `GET /mcp` и остальные методы `/mcp` остаются Streamable HTTP endpoint и не отдают пользовательский интерфейс.
- API страницы настройки находится под `/setup/api/*`. Каждый запрос к нему требует тот же `Authorization: Bearer <token>`, что и MCP.
- Страница может получить токен из URL-фрагмента `#token=...`. Фрагмент не отправляется HTTP-серверу; JavaScript немедленно удаляет его через `history.replaceState` и хранит токен только в памяти вкладки. Если фрагмента нет, страница показывает поле для токена.
- HTML-оболочка публична, но до успешной Bearer-проверки не возвращаются список идентичностей, QR, статусы или другие данные.
- Для страницы задаются строгие CSP, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` и запрет встраивания. Внешние скрипты, стили, шрифты и аналитика отсутствуют.
- Проверка Host/Origin применяется ко всей HTTP-поверхности. На удалённом сервере разрешён только настроенный HTTPS-origin; локально — точный origin выбранного порта.

Обычный браузерный переход на `/mcp` без Bearer-заголовка получает `401`; это штатное поведение. Пользовательская точка входа — `/`.

## Страница настройки

После проверки MCP-токена страница показывает:

1. Список пользовательских аккаунтов: стабильный ID, изменяемое отображаемое имя, Telegram ID/username при доступности и состояние (`connecting`, `waiting_qr`, `waiting_2fa`, `waiting_name`, `ready`, `revoked`, `error`, `disabled`).
2. Кнопку «Подключить аккаунт». Мастер сначала показывает QR; просроченный QR обновляется автоматически.
3. Поле 2FA только после ответа Telegram `SESSION_PASSWORD_NEEDED`. Пароль передаётся один раз по HTTPS или loopback HTTP, не сохраняется и не логируется. После трёх неверных попыток поток завершается; его можно начать заново. После успешного входа третий шаг запрашивает уникальное отображаемое имя. До сохранения имени аккаунт не доступен MCP.
4. Для подключённого аккаунта — действия переименования, отключения/включения и повторной авторизации. Отключение останавливает клиент, но сохраняет сессию. Удаление файлов сессии и Telegram logout в первую версию не входят.
5. Отдельный необязательный список ботов. Бот добавляется по токену BotFather и отображаемому имени; токен проверяется через `getMe` до атомарного сохранения. Ошибка нового токена не меняет существующую запись. Бота можно отключить/включить и переименовать. Удаление/отзыв токена выполняется вне первой версии.

Страница опрашивает короткие статусные endpoints. Одновременно для одного создаваемого аккаунта действует только один QR-поток; повторный запрос возвращает текущее состояние. Разные аккаунты могут проходить авторизацию параллельно. Закрытие вкладки не ломает уже запущенный поток: он живёт до успеха, явной отмены или ограниченного таймаута.

## Идентичности и хранение

Глобальное состояние содержит Telegram `api_id`/`api_hash`, MCP-токен и версию схемы. Они задаются один раз через существующий `setup` либо импортируются из прежней конфигурации.

Каждая пользовательская учётная запись получает неизменяемый случайный ID вида `acct_<base32>` и отдельный файл Telethon-сессии. Отображаемое имя можно менять; инструменты принимают ID, поэтому переименование не ломает конфигурации агентов. Каждый бот получает отдельный ID вида `bot_<base32>` и хранит токен в приватном конфигурационном файле.

Предлагаемая структура:

```text
state/                         0700
  config.json                  0600  schema, api_id/hash, MCP token
  identities.json              0600  labels, enabled flags, bot tokens
  .registry.lock               0600
  accounts/
    acct_xxx.session           0600
    acct_yyy.session           0600
```

Записи выполняются атомарно. Симлинки, hardlink-файлы, чужой владелец и более широкие права отклоняются. Токены, QR URL, 2FA и auth keys не попадают в ответы об ошибках или логи.

При первом запуске текущий однопользовательский формат мигрируется атомарно: глобальные реквизиты остаются глобальными, прежний `account.session` становится первой записью с автоматически созданным `account_id` и именем `Primary`. Если миграция не завершилась полностью, исходные файлы остаются пригодны для повторной попытки. Пустая или неавторизованная сессия мигрируется как запись `revoked`, которую можно авторизовать на странице.

## Реестр подключений

Один процесс приложения владеет реестром идентичностей. Для каждого включённого пользовательского аккаунта создаётся отдельный `TelegramClient`; разные аккаунты никогда не разделяют session-файл. Реестр сериализует изменения конкретной идентичности, но не блокирует операции других аккаунтов.

На старте сервер:

1. захватывает общий файловый lock;
2. загружает и при необходимости мигрирует конфигурацию;
3. поднимает HTTP/MCP независимо от числа авторизованных аккаунтов;
4. подключает все включённые аккаунты в фоне;
5. отражает индивидуальные ошибки в статусах, не завершая весь процесс.

Добавленный через веб аккаунт после успешного входа становится доступен MCP без перезапуска. Отключение аккаунта дожидается текущей операции с ограниченным таймаутом, запрещает новые операции и закрывает его клиент. Завершение процесса закрывает все клиенты и HTTP-соединения.

## MCP-инструменты

- `get_status`: состояние сервера и количество готовых/проблемных идентичностей, без секретов.
- `list_accounts`: пользовательские аккаунты с `account_id`, именем, Telegram identity и состоянием.
- `list_bots`: боты с `bot_id`, именем, Telegram identity и состоянием.
- `list_chats(account_id, limit, cursor)`.
- `get_chat_history(account_id, chat_id, limit, cursor)`.
- `search_messages(account_id, chat_id, query, limit, cursor)`.
- `send_as_user(account_id, chat_id, text, reply_to)`.
- `send_as_bot(bot_id, chat_id, text, reply_to)`.

`account_id` обязателен для чтения и пользовательской отправки; `bot_id` обязателен для отправки ботом. Сервер не выбирает первую или «основную» идентичность автоматически и не переключает отправителя после ошибки. Курсор подписан глобальным MCP-токеном и дополнительно связан с идентичностью, чатом и поисковым запросом.

Если ID неизвестен, отключён, не авторизован или временно недоступен, инструмент возвращает разные безопасные коды (`identity_not_found`, `identity_disabled`, `not_authorized`, `unavailable`). `delivery_unknown` сохраняет прежний смысл: агент проверяет историю именно указанного аккаунта и не повторяет отправку вслепую.

## Bot API

Боты не читают историю пользовательских аккаунтов. `send_as_bot` использует только явно указанный `bot_id`. Для каждого вызова выбирается токен соответствующей записи; токены никогда не входят в URL, структурированные результаты или сообщения об ошибках. Один общий HTTP-клиент может использоваться для всех ботов, поскольку состояние Bot API не хранится в соединении.

## Ошибки и восстановление

- Истечение QR создаёт новый QR в том же потоке; UI обновляет изображение.
- Отозванная пользовательская сессия переводит только соответствующую запись в `revoked` и предлагает повторную авторизацию.
- Ошибка подключения одного аккаунта не влияет на HTTP, MCP, другие аккаунты или ботов.
- Перезапуск во время QR/2FA отменяет незавершённый поток; постоянная запись создаётся заранее со статусом `revoked`, поэтому владелец может повторить вход.
- Повторный Telegram ID не разрешается: после сканирования сервер сравнивает `get_me().id`, закрывает новую сессию и сообщает, какой существующий `account_id` уже подключён.
- Изменения labels/enabled и успешное сохранение бота атомарны. Неопределённый результат отправки никогда не повторяется автоматически.

## Проверки

- Старт без session-файлов и доступность `/` при работающем `/mcp`.
- Отсутствие данных настройки без Bearer-токена; Host/Origin/CSP/no-store проверки.
- Получение QR, обновление по expiry, QR listener до показа, 2FA, три неверные попытки, отмена и перезапуск процесса.
- Параллельный вход двух аккаунтов, запрет дубликата Telegram ID и независимость ошибок.
- Горячее добавление, отключение и повторное включение аккаунта без перезапуска сервера.
- Миграция старого состояния, восстановление после прерванной миграции и сохранение прав 0700/0600.
- Обязательный и валидный `account_id`/`bot_id` во всех инструментах, привязка курсоров к идентичности.
- Два пользовательских аккаунта с пересекающимися `chat_id`: чтение и отправка идут через явно выбранный клиент.
- Несколько ботов, ошибка проверки нового токена и отсутствие влияния на существующих ботов.
- Настоящий MCP SDK поверх HTTP, несколько одновременных клиентов, безопасные логи и неизвестный результат отправки.

Живые проверки выполняются на выбранных владельцем тестовых чатах после веб-авторизации. Тесты с адаптерами не считаются доказательством реальной отправки.

## Развёртывание

Docker Compose и Caddy сохраняются. Внешний URL страницы — `https://<domain>/`, MCP — `https://<domain>/mcp`. Передача MCP-токена через query string запрещена; для удобного открытия допускается только URL-фрагмент, который браузер немедленно удаляет.

Контейнер остаётся однопроцессным и непривилегированным. Постоянный том содержит глобальную конфигурацию и все session-файлы. Резервная копия выполняется только при остановленном сервисе и должна быть зашифрована.
